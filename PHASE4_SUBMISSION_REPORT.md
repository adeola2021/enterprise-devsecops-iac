## 1. Executive Summary

Phase 4 integrated automated threat modeling, static analysis, infrastructure-as-code scanning and policy-as-code enforcement into a GitHub Actions workflow. PyTM generated architecture and threat artifacts; Semgrep and Checkov produced SARIF security findings; and OPA/Rego policies were tested against genuine JSON plans generated by the AWS Terraform provider, alongside Phase 2 regression fixtures.

The latest GitHub Actions workflow completed successfully. The updated Semgrep artifact contained **zero findings**, following remediation of two hardcoded dummy AWS credential findings in test provider configurations. The Checkov SARIF artifact contained **23 findings across 13 rule IDs**. These findings include deliberately insecure test resources and additional hardening opportunities; Checkov is currently configured for **reporting (`--soft-fail`)**, not as a universal blocking gate. The OPA/Rego regression suite passed all four tests, including expected rejection of insecure plans.

**Conclusion:** The defined Phase 4 policy gate demonstrably accepts compliant test inputs and rejects noncompliant test inputs. This does not establish that all repository infrastructure is free of security findings or that the Terraform resources have been deployed.

## 2. Objectives and Scope

The Phase 4 objectives were to:

1. Model application and infrastructure threats automatically and generate reviewable architecture evidence.
2. Scan source and Terraform configurations for security weaknesses.
3. Assess Terraform resources with Checkov and export SARIF evidence.
4. Enforce defined IaC security requirements using OPA/Rego against real Terraform plan JSON.
5. Exercise both compliant and intentionally noncompliant cases in automated CI.
6. Preserve artifacts and execution evidence for independent review.

**Scope:** The GitHub repository and isolated Terraform policy-test modules. The offline Terraform plans used dummy credentials and did not require `terraform apply` or deployment to AWS.

## 7. OPA/Rego Security Controls

The policy implementation evaluates Terraform plan JSON (`planned_values`) and uses configuration relationships where necessary to interpret associated resources. The implemented policy objectives include:

- Requiring S3 server-side encryption with AWS KMS and relevant encryption configuration associations.
- Requiring S3 public-access-block protections.
- Rejecting publicly accessible SSH/RDP ingress, including port-range and standalone ingress-rule cases covered by the policy.
- Enforcing mandatory resource tags: `Environment`, `Owner`, and `Project`.
- Applying relevant existing region and Phase 2 controls.

The policies were tested against **genuine AWS provider Terraform plans**, not only handcrafted fixture JSON. This is important because planned resource values may be unknown before deployment, requiring evaluation of resource relationships and configuration information.

## 10. Risk Assessment, Limitations and Remediation Plan

| Item | Status / implication | Recommended action |
|---|---|---|
| Checkov reports 23 findings | Open review items, including deliberate negative tests | Triage by file and rule; distinguish demonstrations from deployable configurations |
| Secure test module has six Checkov findings | OPA-compliant does not mean fully Checkov-compliant | Assess and harden the positive-test module without invalidating required policy tests |
| Checkov `--soft-fail` | Checkov findings do not block CI | Introduce a scoped severity/rule threshold or a separate blocking production scan after baseline triage |
| Deliberately insecure fixtures and archive | Necessary for negative tests but unsafe to deploy | Clearly label, isolate, and exclude from deployment paths |
| PyTM produces potential threats | Generated count is not a verified vulnerability count | Prioritize and validate threats with owners and mitigations |
| Offline Terraform plans | Demonstrate policy evaluation, not cloud deployment | Validate actual cloud configuration separately before any deployment |
| Security scan scope | Zero Semgrep findings covers only configured scan scope | Maintain rule updates and periodic review of coverage |

## 11. Recommendations and Next Steps
